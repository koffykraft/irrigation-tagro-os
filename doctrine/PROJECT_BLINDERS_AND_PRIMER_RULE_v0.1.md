# Irrigation TAGRO OS — Project Blinders & Primer Rule v0.1

Status: WORKING
Governing source: TAGRO OS Think — Project Blinders & Branch Continuity Doctrine

## 1. Irrigation project blinders

The irrigation application must remain bounded by its current accepted project objective, architecture and domain contract.

Conversation may explore alternate workflows, maps, page structures, controls, hydraulics presentations, AI methods, databases, styles and integrations. Such conversation is not implementation authority.

No AI may widen scope, remove project blinders or reinterpret the project because a new idea appears attractive.

## 2. Material change rule

A material change to the accepted irrigation design creates a project junction.

Examples include:

- replacing the information architecture;
- changing the field-intelligence model;
- changing the hydraulic dependency model;
- changing the page paradigm;
- replacing a major map/drawing approach;
- replacing persistence architecture;
- changing the role of AI in design decisions;
- changing the relationship between farm intelligence and irrigation.

Such a change must be explicitly accepted and recorded before it becomes the new working project state.

## 3. Preserve earlier junctions

Previous branches and states remain recoverable.

A failed branch may still contain one successful component. That component may later be extracted and docked into another branch without reviving the failed branch as a whole.

Abandoned structures may remain in limbo for future recall.

## 4. Primer rule

All early application work is provisional unless explicitly accepted.

A page layout, sidebar, dock arrangement, tile, button, map tool, data-entry pattern, calculation display, database adapter, component library item or visual style is a pencil line or primer coat.

Do not hard-wire it merely because it currently works.

Do not over-engineer it before the underlying decision is mature.

## 5. Maturity governs engineering effort

- SEED: represent the idea cheaply.
- WORKING: make it functional enough to learn.
- REVIEW: make it stable enough to compare and test.
- ACCEPTED: engineer for committed use.
- PRODUCTION: harden, monitor and maintain.

## 6. AI implementation rule

Before modifying the irrigation application, AI must distinguish:

- current accepted project rules;
- current working implementation;
- exploratory conversation;
- candidate change;
- accepted change.

Existing code is never sufficient evidence that an implementation choice is confirmed.

## 7. No accommodation drift

AI must not mirror conversational over-expansion by expanding the build.

If discussion moves beyond the current project blinders, the AI should preserve the idea separately and continue the current project unchanged unless a new junction is explicitly approved.

## 8. Branch memory

Every substantial branch should retain:

- objective;
- starting junction;
- accepted assumptions;
- changes introduced;
- successful reusable components;
- shadows/failures;
- final disposition: active, superseded, limbo, rejected or retired.

## 9. Core rule

The irrigation app is a painting in progress. Pencil lines and primer are necessary, but they are not the finished painting.
